# 仁王3 装备词条修改器（Nioh 3 Equipment Affix Editor）

一个面向 **仁王3（PC）** 的 Python 装备（equipment）词条编辑器，它把修改
**直接写入存档文件**，因此这些修改会跨会话保留——而不是一个
只改内存的修改器。

> **仅供测试学习用，不要用于联机影响游戏平衡。**
> 仁王3 的联机是纯 PvE，所以本工具不可能影响其他玩家。它仍然
> 严格仅供学习/测试使用。使用前请备份你的存档；
> 作者不对任何损坏负责。

本项目有意沿用了 Nioh3-Scroll-Generator 的风格与架构
（纯标准库 Python、失败即拒绝的守卫、子进程隔离的加解密、
静默期指纹校验、原子且持久的写入）。

版本历史与发布检查清单见 [CHANGELOG.md](CHANGELOG.md)。

## 功能特性

* **四个标签页：饰品 / 魂核 / 武器 / 防具** — 魂核（soul core）标签页通过魂核*自己*
  的表来编辑魂核，因为魂核没有 恩宠/套装 词条，并且有独立的词条池：
来自工作簿 `绘卷-魂核词条` 工作表的 287 个 id，加上 绿色星号词条 的
  51 个 ★ id
  来自 `物品总目录`（`大类 = 魂核`），分别以 `data/soul_affixes.json` 和
  `data/soul_items.json` 随包提供。只有当**两个**事实同时成立时，一条记录才被
  判定为魂核——它的头部 id 是 魂核 行*并且*某个槽位指向一个魂核词条——因为
  恰好有一个 id（`0xfb24`）同时列在两个池里，而正是物品表把
  八尺琼勾玉[武士] 这类饰品排除在外。在参考存档上，137 个
  候选解析出 132 个魂核；其余 5 个（两个 `0xda62`，它不在
  魂核工作表里，以及三个携带 `0xfb24` 的饰品）被列为
  未识别并被拒绝，而不是靠猜。与饰品相同的规则
  同样适用：同名固定 词条永不可编辑（每个魂核带两个），等级 上限为
  180，种类 互换只在 魂核 ↔ 魂核 之间进行，且目标种类的固定词条从
  一个真实样本复制。
* **持久化修改** — 解密 PC 用户存档，修补饰品的效果
  槽位，重算用户校验和，重新加密，校验，然后原子替换
  存档，并留下明文备份 + 清单。
* **只读取存档文件** — 列出或编辑饰品时游戏完全不必
  在运行；本工具从不碰游戏内存。
* **定位记录表，而不是假定它** — 记录数组的
  偏移*和*记录步长都是随版本而定的（捕获到的 v2.00.02/v2.01
  布局是 `0x176CCE`、记录为 `0xE8` 字节；一份真实的 v2.21 存档则是 `0x270066`
  、记录为 `0xF0` 字节），所以本工具会从*你的*存档自己的记录
  头推导出这两者，并报告它找到的结果。`scan` 会打印这份诊断（引擎
  偏移、检测到的步长、记录类型与稀有度直方图、原始效果槽
  字节），这样来自本工具尚未见过的版本的存档就可以被反馈回来，
  而不是悄无声息地什么都读不到。
* **饰品靠证据识别，而不是靠类型表** — 在 v2.21 中，
  record+0x00 处的字段保存的是逐物品 id，而不是捕获到的分类 id，
  所以当一条记录的效果槽指出的词条来自随包提供的
  饰品词条 目录时，这条记录就算作饰品。一份真实存档在
  1456 条物品记录中解析出 213 个饰品（其余是武器/防具/绘卷，单独列出）。
  饰品的末尾槽位保存它的 恩宠/套装组合 效果（已在游戏内确认），
  而该表并未列出这些效果，所以这一个槽位会相应地标注，
  而不是标成未知词条。
* **显示每条记录是哪个饰品——并且可以互换它（仅限同分类）** — 同一个
  逐物品 id 会对照工作簿 物品总目录 的 饰品 行来解析
  （以 `data/accessory_items.json` 随包提供，**89 条**；其中两条带有
  存档实测来源，见下文的
  [参考存档](#参考存档)），所以 `list` 和 GUI 会为每条
  记录命名（`种类 0x3e3f 龙笛[武士]`、`0x4987 八尺琼勾玉[武士]`、
  `0xf5bb 凶王耳饰[忍者]`）。在参考存档上实测：**213 个中的 213 个**
  饰品都能解析出来。修改 饰品种类 支持在**同一个中类之内**进行
  （武士饰品 ↔ 武士饰品、忍者饰品 ↔ 忍者饰品），可从 GUI 的 种类 行或
  `edit --kind` 发起，而目标种类的 同名固定 词条是**从正在编辑的存档里
  已有的该种类真实样本**复制而来——绝不凭空编造。见
  [修改种类](#修改种类同分类互换)。
* **固定词条不可编辑（失败即拒绝）** — 每个种类都有自己的
  同名固定 词条（有些种类没有）。当目录把该 id 标为
  `(同名固定)` 和/或该槽位的元数据第 9 字节带有 `0x40` 位时，这个槽位就算作固定；在
  参考存档上实测，两者在全部 795 个已编目槽位上完全一致，零
  例外。固定槽位显示为 `（固定词条，不可修改）`，会被
  `plan_edits` 拒绝，作为*目标*也同样被拒绝（普通槽位不得被改成
  固定词条）。唯一会重写它们的代码是 种类 互换，它复制的是
  目标种类自己的条目。
* **等级 编辑，上限 180** — `edit --level 180` 或 GUI 的 等级 行只会写
  `+0x06`/`+0x08`，并拒绝任何高于 180 的值（参考项目把
  有效等级读作 `min(record +0x06, 180)`，而参考存档正好
  顶到 180）。实测：整个 9.4 MB 的存档只改动 5 个字节（2 个等级
  字节 + 3 个校验和字节）。存储的词条数值**不**随等级缩放（见
  关于 数值 与 等级/`+值` 的已验证说明），所以这是一个被标记为需谨慎的修改：
  GUI 会要求确认，并提示在游戏里核对结果。
* **+値 编辑（物品卡上的 `+N`）** — `edit --plus N` 或 GUI 的 +值 行
  （0..30，参考存档实际使用的范围）只写 `+0x0A` 的两个字节；已用三张
  龙笛[武士] 物品卡显示的 +13 / +18 / +19（记录 #28 / #3 / #521）在游戏内确认。
  与 等级 编辑互不影响（两个方向都是）。
* **实时写入条件显示** — GUI 页脚会显示是否有 仁王3
  进程在运行（绿色 = 可写入，红色 = 需要标题界面确认），因此
  这个条件在点击 写入存档 之前就可见。
* **只允许合法词条的编辑** — 词条目录由
`仁王3词条装备库v2.21.xlsx` 的 饰品词条 工作表，加上 绿色星号词条 工作表里
  适用于饰品 的行（→ 308 个唯一效果 id：276 + 32 条 ★）；任何
  不在表中的词条都会被拒绝（失败即拒绝）。
* **恩宠 编辑（饰品：仅 恩宠 → 恩宠）** — 饰品的最后一个槽位可以被
  改成另一个 `xxx的恩宠`（工作簿标记为 恩宠 或 上位恩宠 的 21 行），
  可从 GUI 的 恩宠 行或 `edit --grace` 发起。物品专属的 套装/专属套装 效果
  （例如 怨恨盖世）和普通 词条 会被拒绝，非末尾槽位和
  不是饰品的记录也一样：这道闸门用的是游戏自己的族字节
  （元数据第 9 字节——参考存档 213 个饰品的全部 196 个 恩宠 槽位是 `0x0C`，
  全部 16 个 套装 槽位是 `0x4C`）。只有该槽位的效果 id 和
  数值会改变；族/子种类字节以及尚未解释的第 11 字节都
  原样保留游戏写入的内容。在真实存档的一个副本上实测：整个
  9.4 MB 的存档只改动 5 个字节——2 个 id 字节和 3 个校验和字节。
* **武器 / 防具的 恩宠/套装 可以替换** — 武器 / 防具页签的【恩宠 / 套装】栏从
  只读显示变成下拉，下拉只列**恩宠族 21 行**（恩宠 10 + 上位恩宠 11）；套装槽置灰
  （只列恩宠族），所以这一槽只能从 恩宠
  换成 套装。规则是只**替换**该记录**已有**的恩宠/套装槽，不凭空新增：参考存档
  实测 497/497 武器、614/614 防具各**恰好一个**恩宠/套装，而且都在第 5 槽；
  记录里没有恩宠槽就带原因拒绝（没有可参照的 metadata 形状，硬写就是猜）。
  一件装备只能有一个恩宠/套装。写入只改这一槽的词条 id 与数值，槽里其余标识——
  种类码 `0x0C00`（=「其他」）、固定位 `0x4000`、★ 位、第 11 字节——原样保留；
  恩宠/套装槽**从来不算固定词条**（固定位不影响它），目标数值只能取恩宠名表
  自己的目录值，名表之外的表外 id 仍然一律拒绝（失败即拒绝）。**CLI 没有跟着变**：
  `edit --grace` 仍然只作用于饰品记录，武器 / 防具的替换入口只有 GUI。
  **已实机核对**：按本工具把恩宠换成另一个恩宠之后，游戏能正常识别该存档
  （仍然建议先在副本上试、留着自动备份）。
* **双加解密后端** — 默认使用随包提供的参考可执行程序
  （`bin/Nioh_Savefile_decrypt.exe`，每遍约 0.4 s）；并以一个
  位级精确的纯 Python 移植版自定义 Nioh AES 作为零依赖
  回退方案（`--python-crypto`，每遍约 32 s）。
* **GUI（Tkinter）与 CLI** — 无第三方依赖。
* **带标记的构建** — `build.ps1` 会把 commit 尾段、源码路径、构建
  时间和语言固化进应用，所以每一份副本都能准确说明自己是什么。一次
  构建大约一分钟完成打包；加上 `-Test` 可以用测试套件把关。
* **经过验证的写入流程** — 静默期双重读取、游戏进程闸门、
  重算校验和、明文备份 + 清单、安装前的分阶段解密校验、
  带自动回滚的写入后校验，以及持久的
  `MoveFileExW` 替换。
* **可以还原的备份** — 每次写入都会先保存一份带时间戳的明文
  副本加一份清单；`restore` 会列出它们，并能把任意一份放回去（重新加密，
  并对被替换的内容留一份安全副本）。见
  [备份与恢复](#备份与恢复)。

## 运行要求

* Windows 10/11、Python 3.10+（仅标准库：`tkinter`、`ctypes`、`zipfile`）。
* 一份真实的 仁王3 PC 存档，位于
  `%LOCALAPPDATA%\KoeiTecmo\NIOH3\Savedata\<SteamID>\SAVEDATA??\SAVEDATA.BIN`。

## 快速开始

> **写入之前：关闭游戏，或让它停在标题画面。** 修改是
> 写入存档文件的，所以游戏不能已经载入该存档（见
> [安全模型](#安全模型)）。每次写入都会打印这条要求；GUI
> 会一直显示它，并在确认对话框里再重复一次，而且——只要有游戏进程在运行——
> 还额外要求你勾选「游戏停在标题界面」这个确认框（CLI：`--at-title-screen`）。

```powershell
# GUI
python launch_editor.py

# CLI：列出存档及其饰品记录
python launch_editor.py list

# CLI：诊断某个存档的记录表（只读；无需游戏运行）
python launch_editor.py scan

# CLI：只读的完整性报告（JSON）
python launch_editor.py check

# CLI：把 3 号记录的效果槽 1 改为词条 0x0B32（数值 200），并写回
python launch_editor.py edit --record 3 --edit 1:0x0B32:200

# CLI：演练（校验一切，但不写入任何东西）
python launch_editor.py edit --record 3 --edit 1:0x0B32:200 --dry-run

# CLI：把 3 号记录的 恩宠 换成另一个——可以按 id，也可以按唯一名称
python launch_editor.py edit --record 3 --grace 0x4fa3
python launch_editor.py edit --record 3 --grace 稻荷神 --dry-run
#   只允许 恩宠 → 恩宠；套装/专属套装（例如 怨恨盖世）和普通 词条 会被
#   连原因一起拒绝，并且不写入任何东西。

# CLI：修改 等级（1..180；只改 +0x06/+0x08 和校验和）
python launch_editor.py edit --record 3 --level 180 --dry-run

# CLI：在同一个中类内互换 种类（武士饰品 ↔ 武士饰品）
python launch_editor.py edit --record 3 --kind 八尺琼勾玉[武士] --dry-run
python launch_editor.py edit --record 3 --kind 0x4987 --dry-run
#   目标种类的 同名固定 词条从本存档中的一个真实样本复制；
#   跨分类互换、没有样本的种类、以及有歧义的种类都会被拒绝。

# CLI：只做明文备份
python launch_editor.py backup

# CLI：列出该存档的备份，然后恢复最新的一个（先演练）
python launch_editor.py restore --list
python launch_editor.py restore --from latest --dry-run
python launch_editor.py restore --from latest

# CLI：版本/构建信息（commit 尾段、来源、构建时间、语言）
python launch_editor.py --version
python launch_editor.py version --json
```

### 如果 读取数据（或 `list`）找不到记录

游戏**不**需要在运行——读取只接触存档文件。
结果为空或近乎为空，意味着本工具无法识别该存档的
记录表，而数组偏移和记录步长*两者*都是
随版本而定的：捕获到的 v2.00.02/v2.01 布局把 400 条 `0xE8`
字节的记录放在 `0x176CCE`，而一份真实的 v2.21 存档则在
`0x270066` 保存 2000 条 `0xF0` 字节的记录。用捕获到的步长扫描这样的存档，
每 `0xE8 × 30 == 0xF0 × 29` 字节才命中一条真实记录，
看起来就和「没有饰品」一模一样。因此本工具会从存档自己的头部推导出这两者，
并报告它找到的结果：

```powershell
python launch_editor.py scan          # 人类可读的诊断
python launch_editor.py scan --json   # 同上，机器可读
```

报告会说明记录表被定位在哪里（或是否被定位到）、它用的是什么
步长、证据有多强、记录类型与稀有度直方图、
等级范围，以及若干条记录的原始效果槽字节。如果这些数字与游戏显示的不符，
请把该输出连同你的存档版本一起反馈回来。

当你手上有存档文件本身时（不需要游戏内参照），这个深度
只读检查器会用统计而不是假定来回答接下来的两个
问题：

```powershell
# 表在哪里、哪个效果槽基址是真的、哪些记录是饰品？
python tools\inspect_save.py --config D:\path\to\editor.json --records 10
python tools\inspect_save.py --save "D:\...\SAVEDATA00\SAVEDATA.BIN" --json report.json
```

* **效果槽基址扫描** — 对每一个候选基址，它统计 `base + k*0x18 + 4` 处的
  u32 值中有多少个是随包目录里*已知的 饰品词条 id*。
  任意字节命中该目录的概率约为 `276/2**32`，所以真正的
  基址会以数量级的差距凸显出来，而捕获到的 `0x34` 是被证实
  而不是被信任。相隔整整一个步长的基址读到的是同一格点平移后的结果
  （它们会漏掉第一个或最后一个真实槽位），所以它们被标注为
  `与 0x34 同格`，而不是被悄悄当作独立证据来排序。
* **饰品候选** — 占用槽位*全部*都指向目录条目的记录，
  按槽逐个列出 `名称 / id / 数值 / 标识`；带有
  未知 id 的记录会单独报告。
* **按类型汇总** — 统计数组中每种记录类型的数量、等级范围、稀有度、
  占用槽位直方图和目录命中率。

一切都是只读的：存档只在内存中解密，不会创建任何状态目录，
并且报告结尾会说明这一点。

### 发布构建：单个单文件可执行程序

把 `Nioh3EquipmentAffixEditor.exe` 下载/复制到任意位置并运行它。发布版中**没有
安装程序、没有 `dist/` 文件夹、也没有 `.py` 文件**：程序
需要的一切都在那一个文件里。

* **双击**它即可打开 GUI。
* 要使用 CLI 就从终端运行它（GUI 会隐藏启动它的那个控制台，
  但 CLI 运行会保留它）：

  ```powershell
  .\Nioh3EquipmentAffixEditor.exe list
  .\Nioh3EquipmentAffixEditor.exe check
  .\Nioh3EquipmentAffixEditor.exe edit --record 3 --edit 1:0x0B32:200
  .\Nioh3EquipmentAffixEditor.exe restore --list
  .\Nioh3EquipmentAffixEditor.exe version
  ```

**首次运行会把并列文件解包到 exe 旁边**（这是有意
设计的，这样你可以阅读和编辑它们）：

| 路径 | 内容 |
| --- | --- |
| `config/editor.json` | 参数文件：存档根目录、账号/存档位过滤、加解密后端、备份根目录、GUI 默认值 |
| `assets/` | 程序图标（`app.ico`）与 logo（`logo.png`、`logo-64.png`、`logo-32.png`） |
| `data/accessory_affixes.json` | 编辑器用于校验的合法词条目录 |
| `data/grace_affixes.json` | 恩宠/套装组合 名称表——给饰品和武器 / 防具的恩宠/套装槽命名与校验，绝不用来放行表外 id |
| `bin/Nioh_Savefile_decrypt.exe` | 随包的加解密辅助程序（快速路径；纯 Python 是回退方案） |
| `third_party/source-data/` | 原始 `.xlsx` / `.CT` 输入（你可以自己重新生成目录） |
| `README.md`, `CHANGELOG.md` | 文档，复制一份以便离线阅读 |
| `.extracted-manifest.json` | 记账文件（本程序写过的每个文件的哈希） |

以下规则使得把它放在你自己的文件旁边是安全的：

* 你编辑过的文件**绝不会**被之后版本的 exe 覆盖——
  只有内容仍与解包时一致的文件才会被刷新。
* 删除一个文件后，下次运行会把它恢复回来。
* 如果该文件夹是只读的（例如 `Program Files`），程序仍会运行，
  只是改为从可执行程序内部读取资源，而不是写出它们。
* 把 exe 放在你选择的可写文件夹里；备份会写到
  同一个文件夹（`_nioh3_equipment_affix_backup/`），除非配置另有指定。

可执行程序本身会把它的 Python 运行时解包到每会话惯用的
`%TEMP%\_MEIxxxx` 目录（单文件程序的标准行为，退出时删除）；
上面列出的文件是唯一会留在磁盘上的东西。

## 备份与恢复

**每次写入都会先备份存档。** 备份保存的是*解密后*的字节，所以
恢复不是一次文件复制：本工具会像一次编辑那样把它们重新加密。

备份放在哪里——`<state root>` 是 `config/editor.json` 里的 `backup_root`，否则
就是存放 exe 的文件夹（从源码运行时则是当前目录）：

```text
<state root>/_nioh3_equipment_affix_backup/
    account-<steam id>/          # 例如 account-76561198000000000
        slot-<NN>/               # 例如 slot-03，对应 SAVEDATA03
            SAVEDATA-<YYYYmmdd-HHMMSS>-<uuid8>-plain.bin
            backup-manifest.json
```

| 文件 | 内容 |
| --- | --- |
| `SAVEDATA-*-plain.bin` | 编辑器读到的那份存档原样，**已解密**（`RNNUSR`，`0x9001B0` 字节）——一份明文备份，*不是* `SAVEDATA.BIN` 的副本 |
| `backup-manifest.json` | schema、账号、存档位、`created_at`、`main_save_sha256`（加密文件当时的样子）以及 `plain_backup_sha256` |

备份绝不会被覆盖——每一份都有自己的时间戳名字——所以它们会
累积起来，你可以回滚到任意时间点。

```powershell
# 列出该存档的备份，最新的在前（只读）
python launch_editor.py restore --list

# 演练：校验备份和每一道闸门，不写入任何东西
python launch_editor.py restore --from latest --dry-run

# 恢复最新的一个；也可以用 --from 2（索引）或 --from D:\my-plain.bin
python launch_editor.py restore --from latest
```

GUI 有对应的**恢复备份**（restore backup）按钮：它会列出备份
及其时间和大小，然后在写入前请求确认。

恢复本身也是可逆的：当前存档在被覆盖*之前*会先备份，
并且报告会打印那份安全副本去了哪里
（`safety_backup_dir`）。当备份的 SHA-256 不再
与它的清单一致，或这些字节不是 `0x9001B0` 字节的合法 `RNNUSR` 存档时，它会拒绝写入，
并且它和编辑一样遵守同一道游戏运行闸门、静默期复查
和 `SAVE_SYNC_ACTIVE` 拒绝。

报告里的 `matches_original_save` 说明被恢复的文件是否
与当初备份的文件逐字节一致。它可能会诚实地为 `false`，原因
值得了解：参考加解密工具会在**两个**方向上把存档最后 8 个字节
——它们位于加密区域之外——清零，所以备份
无法记录它们。于是恢复会把这些字节按游戏写入的样子保留下来，
而不是把它们清零（`tail_source: "on-disk"`）：载荷被恢复，
尾部被保留，报告会准确说明这一点。使用纯 Python 后端时
尾部能原样往返，逐字节一致的恢复会被报告为 `true`。

> 游戏会在 `SAVEDATA.BIN` 旁边保留它自己的 `BACKUP.BIN`。本工具从不
> 读写它；它只出现在指纹校验里，所以正在运行的游戏
> 往那里写入仍然会被算作有活动。

## 构建

```powershell
# Release：固化构建标识、构建单文件 exe、
# 在一个全新文件夹里做冒烟测试，然后打包成 zip -> dist/
# （单元测试套件不包含在内：传 -Test 才会包含）
powershell -File .\build.ps1

# 同上，但先做校验——发布一条 changelog 条目之前用它
powershell -File .\build.ps1 -Test

# 先清掉旧的 dist/ 产物（只清 Nioh3EquipmentAffixEditor* 条目）
powershell -File .\build.ps1 -Clean -Test

# 只刷新工作树的构建标识（不产生 dist，不打包 zip）
powershell -File .\build.ps1 -Configuration Debug

# 只跑这个测试模块，例如在迭代 CLI 的时候（-TestPattern 隐含 -Test）
powershell -File .\build.ps1 -Configuration Debug -TestPattern test_cli.py

# 更快的迭代 / 自定义解释器
powershell -File .\build.ps1 -SkipZip -Python D:\Python310\python.exe
```

`build.ps1` 会解析解释器、读取 git 事实、生成构建
标识、在 `dist\` 下准备一棵可运行的目录树，并对那份暂存副本做冒烟测试
（它必须报告被固化的 commit，而不是 git 现在说的那个）。单元测试
套件是**可选的**：默认构建是打包构建，会跳过它，因为
测试套件要跑几分钟，而打包的每一步都不依赖它——最终
报告总会写明 `单元测试 : 已运行 / 未运行`，所以构建日志永远不会被
误当成一次经过验证的构建。参数：`-Python`、`-Configuration
Release|Debug`、`-OutputDirectory`、`-PyInstallerPython`、`-Test`、`-TestPattern`
（隐含 `-Test`）、`-PureCryptoTests`（隐含 `-Test`）、`-SkipZip`、`-Clean`、
`-Quiet`，外加遗留的 `-SkipTests`（如今是空操作，因为跳过已是
默认行为）。它能在 Windows PowerShell 5.1 和 PowerShell 7+ 上工作。

> `build.ps1` 是刻意以**带 BOM** 的 UTF-8 保存的：Windows PowerShell
> 会用 ANSI 代码页（zh-CN 上是 GBK）读取没有 BOM 的脚本，那会
> 破坏它的中文消息并导致解析失败。编辑时请保留 BOM。

### 版本信息

每个版本展示面都报告同样的四项事实：

```text
Nioh 3 Equipment Affix Editor v1.0.0
commit    : 34cca8de（提交号后 8 位） （构建时工作区有未提交改动）
来源      : D:\wherever-you-put-it\Nioh3EquipmentAffixEditor
加密组件  : D:\wherever-you-put-it\Nioh3EquipmentAffixEditor\bin\Nioh_Savefile_decrypt.exe
构建时间  : 2026-09-19T11:01:52+08:00
语言      : CPython 3.10.10 (仅标准库 / stdlib only, 含 tkinter GUI)
```

| 事实 | 含义 |
|---|---|
| `commit` | git commit id 的**最后 8 个字符**（项目约定，不是通常的前缀） |
| `来源` / `加密组件` | 正在运行的那份副本**此刻在哪里**：存放可执行程序的文件夹，以及它从那里读取的加解密组件。移动 exe，这一项就跟着变——不需要重新构建 |
| `构建时间` | 本地构建时间，带 UTC 偏移的 ISO-8601 |
| `语言` | 构建面向的语言/运行时（仅 CPython + 标准库） |
| `（构建时工作区有未提交改动）` | 是**打包那一刻**的记录：表示当时工作区有未提交改动，不代表现在也脏。在干净提交上打出的正式版不会出现这一句 |
| `构建来源` | **不显示**。构建时所在的文件夹只记录在 `BUILD-INFO.txt` 里供排查用——它说明的是构建机，而不是你正在运行的那份副本 |

它出现在哪里：

* `python launch_editor.py --version`（或 `version` 子命令；加上 `--json`
  可得到机器可读的输出），
* GUI 页脚，以及用于完整横幅的**版本信息**按钮（完整 commit、
  分支、组件 SHA-256、信息来源），
* 项目根目录和暂存的 `dist\` 目录树里的
  `BUILD-INFO.txt` / `BUILD-INFO.json`，还有构建日志本身。

`tools/make_build_info.py` 会生成 `nioh3_equipment_affix_editor/_buildinfo.py`
（固化的事实，运行时导入）、`BUILD-INFO.json` 和 `BUILD-INFO.txt`。它
通过重新导入生成出来的模块并比对每一个
字段来校验自己的输出，如果短 commit 不是恰好 8 个字符就会
让构建失败。生成的模块、两个 `BUILD-INFO.*` 文件和 `dist/` 都是被 gitignore 的
构建产物：在下次构建之前，一份全新检出的代码会报告实时的 git 信息
（`信息来源: git`）以及 `构建时间: 未构建（源码运行）`。

## 重新生成词条目录

```powershell
python tools/build_affix_db.py            # 写出 data/accessory_affixes.json
                                          #   和 data/grace_affixes.json
python tools/build_affix_db.py --dry-run  # 只解析 + 报告
```

默认来源是随包的那份副本
`third_party/source-data/仁王3词条装备库v2.21.xlsx`（出处与授权见该文件夹的 README）；
传入一个显式路径（xlsx 或 `A1=...` 的 TSV 转储）即可覆盖。
构建器按效果 id 去重，并把任何
同 id/不同值的冲突记录到目录的 `conflicts` 字段里，而不是
悄悄挑一个。

一个工作簿产出两张表，它们被刻意分开：

* **`data/accessory_affixes.json`** — 饰品词条 工作表（276 个 id）**加上 绿色星号词条
  工作表里可出现在 饰品 上的 32 个 ★ id**（共 308 个 id）
  编辑器接受为修改的内容；其他任何东西都失败即拒绝。
* **`data/grace_affixes.json`** — 词条总目录 的 恩宠/套装组合 行（77 个 id：
  恩宠 10、上位恩宠 11、武士套装 34、忍者套装 22）。它给饰品和武器 / 防具的
  恩宠/套装槽命名与校验（`0x71f6 不动明王的恩宠（上位恩宠）`），而不是显示一个
  未知 id；这张表只用于命名与校验，绝不用来放行表外 id——名表之外的 id 一律被
  拒绝（失败即拒绝）。饰品的恩宠路径（GUI 的 恩宠 行、`edit --grace`）只允许
  恩宠 → 恩宠，所以对饰品来说那 21 行 恩宠/上位恩宠 才是允许的**目标**，
  那 56 行 套装 对饰品不可写：编辑器要求被替换的槽位带有 恩宠 族字节（0x0C），
  而一个 专属套装 效果（例如 怨恨盖世，0x4C）从来不会带它。**武器 / 防具不受
  这条限制**：它们的恩宠槽也只列恩宠族 21 行，恩宠槽可以换成 套装
  （见 [武器 / 防具标签页](#武器--防具标签页)）。
* **`data/accessory_items.json`** — 物品总目录 的 饰品 行（89 行 → 88 个 id：
  武士饰品 46、忍者饰品 42；有一个 id `0x1521` 被列了两次——八咫镜[武士] 和
  [忍者]——这一点被记录在表的 `conflicts` 字段里，而不是被
  藏起来）。这才是饰品**是什么**，以记录头部的逐物品
  id 为键，而且它和上面的表一样只用于显示：这些 id 与 词条 id
  处于不同的空间（实测：与 276 个词条 id 和 77 个
  恩宠/套装 id 零重叠），`list`/GUI 只是用它们给记录命名。

## 已验证的事实与未验证的边界

对照参考可执行程序验证过（黄金值取自它的
调试输出以及整文件逐字节比较）：

* `_key_setup` 头部密钥/IV 对逐字节一致
  （`CD1F3135…84B` / `1BDFDD57…925` / `CD958C0E…4D5` / `FD4C40A2…7BD`）。
* 头部密钥流前缀与观察到的 `31d530acb6d67a46` 一致。
* 整文件加密在被加解密覆盖的区域里与 exe 逐字节一致；
  只有尾部 8 个字节（在加解密范围之外）不同，而
  写入器会从磁盘上的文件恢复这些字节。
* 移植过来的 S-box/RS-box 表与参考 `aes.c` 逐字节一致。

有用的加解密发现（记录下来是因为它们很容易搞错）：

* 参考实现的**解密分支并不是它加密分支的逆**：
  它启用的 `rsbox` 是它 `sbox` 的副本，而那个自定义 S-box 甚至不是
  一个置换（164 个不同值、69 个重复、92 个不可达）。解密是
  通过与加密产生的*同一个* ECB 密钥流做 XOR 来完成的，这也正是
  本项目所做的事；`NiohAes.decrypt_block` 的存在只是为了精确镜像
  `aes.c`，流水线从不使用它。
* 头部那一遍用 22 个计数器块覆盖全部 `0x158` 字节，也就是
  最后一个块只被部分使用。把它截断（用整数除法而不是
  向上取整）会悄无声息地让最后 8 个头部字节不被加密。

| 项目 | 值 |
|---|---|
| 存档大小 | `0x9001B0`（头部 `0x158` + 主体 `0x900058`） |
| 加解密覆盖范围 | `[0, 0x158 + 0x900050)`；最后 8 个字节原样保留 |
| 记录区域 | 运行时定位（捕获到的参考布局：`0x176CCE`，400 个槽位 × `0xE8`；真实 v2.21 存档：`0x270066`，2000 个槽位 × `0xF0`） |
| 记录步长 | 按存档从识别出的记录检测（会扫描 `0xE0`/`0xE8`/`0xF0`/`0xF8`/`0x100`） |
| 效果槽 | 7 个槽位 × `0x18`，从 `0x34` 开始——已在真实 v2.21 存档上确认 |
| 槽位字段 | `<6I`：prefix@0、effect_id@4、value@8、metadata@0xC、tail_0@0x10、tail_1@0x14 |
| 数值语义 | 槽位 `+0x08` 等于目录自己的 `value`（例如 `精力恢复速度 +3.0%` → 30）——已在真实存档上确认 13/13 |
| 校验和 | 主体 `[0x190, 0x900190)`，按 `0x400` 分块；seed@`0x900190`、value@`0x900194` |
| 词条编码 | bytes0-3 效果 id、bytes4-7 数值、byte9 bit6 固定、byte10 bit2 星|

记录区域是怎么找到的：一个槽位由参考项目自己的
测试来识别——类型字和等级字各自镜像自己（`type@0 ==
type@2`、`level@6 == level@8`），类型不为零，并且该槽位要么是
绘卷类型，要么在 `@4` 处有 `1`。那个 `@4` 字是账号 id
的中间 16 位（这种量级的 Steam64 id 在那里总是带 `0x0001`），
这正是让该判据保持稳定的原因。被识别出的槽位按「偏移对
候选步长取模」分组；其最大剩余类所容纳的记录比其他任何类都多一个
数量级的那个步长就是该存档的真实步长（某个存档：`0xF0` 上 1457
条记录，而 `0xE8` 上 58 条），而那个类的跨度就给出了数组。
要求镜像字是有意义的：一个空闲的效果槽保存的是 `0xFFFFFFFF`，
否则它会把自己镜像成一条假的嵌套记录。一个随机块通过的概率
约为 `1/2^48`，所以命中就是证据，而一个没有此类
证据的存档会失败即拒绝，而不是去编辑猜出来的字节。

哪些记录是饰品：随包目录只包含 饰品词条，所以一条
占用效果槽指向目录 id 的记录就是饰品，而词条从不命中
目录的记录（武器、防具、绘卷）则不是。在 v2.21 中这
是唯一可行的规则，因为 record+`0x00` 处的字段保存的是逐物品
id（`a5 6f a5 6f` = 自我复制的 `0x6FA5`），而不是捕获到的分类 id。
因此一份真实存档解析出 **1456 条物品记录中的 213 个
饰品**。

一次编辑实际写入的是什么：该槽位的 `effect_id` 和 `value` 字段。
`metadata` 字段（预计 固定/星 标志位就住在那里）**绝不**被
GUI 修改，因为这些位在槽位层面的编码还没有
对照真实存档确认过；当你知道自己想要什么时，CLI 可以用
`--edit <slot>:<id>:<value>:<metadata>` 显式设置它。选择一个
id 已经占据该槽位的 词条 会被视为「无变化」，不写入
任何东西。

> **⚠️ 诚实的边界：** 记录步长、效果槽基址（`0x34`）、
> `effect_id` 位置（`slot+0x04`）以及数值语义（`slot+0x08`）
> 现在都已对照一份真实解密后的 v2.21 存档确认，并且对该存档的一份副本的写入
> 只改动了**恰好 5 个字节**（3 个在目标槽位里，2 个在校验和
> 字段里）。一份真实存档还确认了游戏内布局：每个饰品都以
> 一个 恩宠 或 套装组合 效果结尾（例如 龙笛 上的 稻荷神的恩宠），其名称来自
> 工作簿的 词条总目录——该存档的 231 个末尾槽位中，215 个被命名，
> 而跨 12 个种类的 16 个 id 根本不在工作簿里，所以未命名的槽位
> 仍会读作 `恩宠/套装词条（表外，id=…）`。仍未验证的：哪个记录 id
> 属于哪个*物品*（游戏的物品名表不在存档里），以及
> `metadata` 各位的含义（工作簿的第 9/10 字节确实与存档中
> 恩宠（`0x0C 0x02`）和 套装（`0x4C 0x01`）代码所保存的一致，但那只是
> 单一存档的观察，不是确认）。**先在你的
> 存档上运行 `list`（或 `scan`），确认列出的记录和词条看起来正确，并保留
> 自动备份**，然后再写入。
>
> **特别是 恩宠 编辑：** 「只允许 `xxx的恩宠` → 另一个 `xxx的恩宠`」这条规则是
> 由三个独立事实共同保证的——该槽位的族字节（0x0C，在该存档的
> 全部 196 个 恩宠 槽位上测得，而全部 16 个 套装 槽位上是 0x4C）、工作簿的 归属
> （仅 恩宠 / 上位恩宠）以及末尾槽位的位置。**未**验证的：
> 上位恩宠 在游戏里是否受等级/难度限制（本编辑不检查
> 这一点）、元数据第 10 字节（0x02 vs 0x0A）和第 11 字节（0x00/0x18/0x29/0xDB/…
> 在*同一个* 恩宠 出现在不同饰品上时）究竟意味着什么——因此两者都
> 是从被替换的槽位复制而来，而不是凭空编造；以及这样的互换之后，
> 游戏内的物品列表是否会干净地刷新（只能载入存档
> 看一眼）。如果互换后出现异常，就恢复自动备份。
>
> 武器 / 防具的 恩宠/套装 替换共用上面这套边界（写入时 metadata 从被替换的槽原样
> 保留，上位恩宠 是否受等级/难度限制仍未查），其中**「恩宠换成另一个恩宠」已实机核对：
> 游戏能正常识别**；套装按规则不可替换。
>
> **饰品种类（它是哪个饰品）和 等级 是可写的，但受下面这些
> 限制。** 该字段是已知的——记录头部 `+0x00` 处的逐物品 id，
> 在 `+0x02` 处有一个镜像（在全部 213 条记录上相等），它能解析到
> `data/accessory_items.json`，其中 212 条如此。这两个字段都只通过
> [修改种类](#修改种类同分类互换) 和
> [修改等级](#修改等级) 里的规则写入，并且两者都是先在真实存档的一份副本上实测，
> 然后才写入。**未**验证的、以及本工具因此拒绝或标记的：
> (1) 被互换记录的*现有*普通效果槽会怎样——一次
> 种类互换不会碰它们，所以一个 八尺琼勾玉 可以保留原本只有
> 龙笛 才该带的词条（游戏会显示它们、修复它们还是拒绝它们——未知），所以
> 该编辑在 CLI 里被标记为需谨慎、在 GUI 里需要确认；(2) 一个
> 物品专属的 专属套装 效果（例如 凶王耳饰 上的 怨恨盖世）是否必须匹配新种类——
> 套装 槽位*不会*被互换重写，所以那里也可能出现同类的
> 不匹配；(3) 游戏是否会根据 等级 重算显示数值——
> 存储的词条数值与等级无关（已实测），所以任何变化都必须是
> 游戏自己的推导；(4) `0x1521` 映射到两个不同的物品（八咫镜[武士] 和
> [忍者]），因此被报告为未列出，而不是靠猜。在一次
> 种类互换/等级编辑之后请在游戏里核对；自动备份可以恢复先前的状态。

### 修改种类（同分类互换）

`edit --kind <名称|id>`（CLI）或 GUI 的 种类 行会互换一条记录是哪个饰品，
受三条失败即拒绝的规则约束：

1. **仅限同一个中类** — 记录自己的 id 和目标 id 必须都是 物品总目录 的 饰品 行，
   并且中类相同（`武士饰品` ↔ `武士饰品`、`忍者饰品` ↔
   `忍者饰品`）。跨分类互换，或者一个没有表行的 id（包括
   `0x5c5f`），都会被连原因一起拒绝。
2. **固定词条是复制来的，绝不是编造的** — 目标种类的 同名固定 词条
   是从*你的*存档里已有的该种类真实副本读出的：它的槽位索引、
   效果 id、数值和元数据第 9 字节。在参考存档中对 60 个带固定
   词条的种类实测，这些字段在同一
   种类的每一个副本上都一致（58/60；两个例外是 八咫镜 变体，它们作为
   有歧义被拒绝）。元数据第 10/11 字节（只有 25/60 个种类一致）和槽位 `prefix`
   （4 个种类不一致）是**逐实例**的，所以它们按原样逐字节
   保留。如果目标种类在这个存档里没有副本，互换会被拒绝——本工具
   不会去猜一个固定词条。
3. **普通槽位和 恩宠/套装 槽位不受触碰** — 只有头部 id（两份
   镜像副本）和固定槽位会改变。在真实存档的一份副本上实测：
   互换 3 号记录（龙笛[武士] → 八尺琼勾玉[武士]）改动了 7 个字节
   （4 个头部字节 + 固定槽位的 id/数值）以及 3 个校验和字节，并且
   该记录回读为 `0x4987 八尺琼勾玉[武士]`，带
   `(同名固定)组合效果的所需装备数 -1 id=0x53d4 数值=1`。

### 魂核标签页

`python launch_editor.py souls`（CLI，只读）或 GUI 的 魂核 标签页用同样的三种编辑
处理魂核，并通过 `--soul` 切换到魂核的表：

| 项目 | CLI | 规则 |
| --- | --- | --- |
| 魂核词条 | `edit --soul --record N --edit 3=<名称\|id>` | id 必须是 `种类 = 魂核` 的 287 行 `绘卷-魂核词条` 之一 |
| 等级 | `edit --soul --record N --level 180` | 1..180，只写 `+0x06`/`+0x08` |
| 种类 | `edit --soul --record N --kind <名称\|id>` | 魂核 ↔ 魂核；固定词条从真实样本复制 |

* **没有 恩宠/套装** — 这一点是闸门自然导出的结果，而不是特例处理：
  恩宠 id 根本不在 魂核 池里，所以 `--soul --grace` 会被直接拒绝，
  并且该标签页没有 恩宠 行。在该存档上实测：0 个已确认魂核带 恩宠/套装。
* **同名固定词条不可修改** — 每个已确认的魂核都带**两个**固定词条
  （`#12 魑魅的魂核`：`id=0xd0c5` 和 `id=0x74df`）；两行都被禁用并
  在标签页里标注为 `固定词条，禁止修改`，引擎也会拒绝。
* **验证** — 工作簿自己的 固定词条代码 在全部 132 个
  已确认魂核上与存档一致，**0 处不匹配**，这也正是目录标记在这里同样是
  正确固定词条证据的原因。

### 武器 / 防具标签页

武器 与 防具 是 饰品 / 魂核 旁边的两个标签页。它们读的是同一份已解密字节——点一次
读取数据 四个标签页都会填好——流程也和饰品标签页一样：选记录 → 改词条槽 →
预览改动 → 应用修改 → 写入存档（写入路径**就是**那个标签页的代码，连副本闸门都是
同一个：只写你指定的副本，从不改动原档）。

* **候选词条属于这件装备**——刀 用近战词条表，弓 / 火枪 / 大炮 用远程词条表，防具用
  防具词条表；此外这条词条的「装备种类」标签还必须与这件装备接受的标签相交，所以
  只标「近战」的词条绝不会出现在弓上。这两项判定都由引擎负责
  （`equipment_affix_allowed`），标签页不自己重写一套。同名固定词条根本不会出现在
  可写候选里：它们只能由 改种类 带入，这也是固定槽会置灰显示 `固定，不可修改` 的原因。
* **4 轴筛选**——类型 / 种类 / 恩宠·套装 / 武士·忍者，每个轴只列出另外 3 个轴仍然允许
  的取值。已经没有记录的取值会保留成 `xxx（当前无记录）`，而不是被悄悄重置，这样列表
  为空时你能看出是哪个筛选造成的。
* **逐槽搜索**——每个槽有自己的下拉列表；打字只收窄这一个槽，空格表示「都要命中」，
  回车接受唯一命中，2 条及以上必须从该槽的列表里挑。
* **恩宠 / 套装 可以替换（GUI）**——右下角的【恩宠 / 套装】栏不再是只读显示，而是
  下拉，下拉里只有恩宠族 21 行（恩宠 10、上位恩宠 11、
  武士套装 34、忍者套装 22），所以这一槽可以从 恩宠 换成 套装；规则与实测口径见
  [功能特性](#功能特性)。恩宠·套装 筛选轴照旧按它筛记录。
* **等级 / +値**——两个标签页都是 180 与 30，取自 `class_limits_for_record`；
  `data/equipment_ranges.json` 里按类别实测出来的最大值只是证据，不会被当成上限。
* **无中生有（实验性：需要进游戏实测确认）**——按钮在**页签最下方一个独立的框**里，与上面的
  编辑区隔开；【应用修改】不会碰它（那个按钮只改写当前选中的已有记录）。武器 / 防具的框里
  还能填**稀有度**（留空就沿用模板）。按钮和它的引擎入口都在，也有 34 项测试，
  但造出来的装备还没有在游戏里确认过。模板优先取同种类的真实记录；没有同种类时改用
  同类型（小类）记录，并把不适用的槽清空——写入之前就会把这些原因显示出来。

### 修改稀有度（品质）

四个页签（饰品 / 魂核 / 武器 / 防具）都在 等级 与 +値 旁边多了一行「稀有度」：
填上新数值后点【应用稀有度】——同一套 计划 → 应用 → 写入存档 流程，同一句
`（内存中，尚未写入存档）` 提示，没点【写入存档】之前不会落到磁盘上。

* **只改品质字段**——`+0x30` 的低 4 位（写成 `0` 时还会清掉 `+0x31` 的低 4 位，
  因为读回时 `+0x30` 为 0 会退回它）。词条 / 等级 / +值 / metadata 都不动，
  `+0x30` 的高 4 位原样保留。
* **上限按记录所属大类取**，查的是随包的 `data/equipment_items.json`：
  武器 / 防具 / 饰品 ≤ 4（神器）、魂核 ≤ 3（特大名器）。id 不在那张总目录里的记录
  **一律拒绝**，绝不猜一个上限。
* **一张表、一个出处**——`nioh3_equipment_affix_editor/limits.py` 是 等级 180、
  +值 武器/防具/饰品 30、魂核 15、绘卷无 +值、以及 稀有度 武器/防具/饰品/绘卷 4、
  魂核 3 的唯一来源。
* **游戏内颜色**——0 白色、1 黄色、2 蓝色、3 紫色、4 绿色、5 橙色。颜色只用于
  显示，永远不是上限。橙色（5）在当前周目（三周目：本体 + DLC1）不可达；等 DLC2 /
  四周目开放后才可能开放，届时只需改 `limits.py` 里那一张表。
* **切记录会刷新这一行**——框里永远是刚选中那条记录的值与它自己的范围；没选记录时
  置灰。被拒绝时用对话框显示引擎给的中文理由。

### 筛选、关键词搜索、数值区间与「无中生有」

应要求新增的五种行为，全部失败即拒绝，并且都能从
GUI 和 CLI 两边使用：

| # | 项目 | GUI | CLI | 规则（证据） |
| --- | --- | --- | --- | --- |
| 1 | 不能再加固定词条 | 固定行被禁用 | 任何对固定 id 的写入都被拒绝 | 同名固定 词条是*物品本身是什么*的一部分；0→1 / 1→2 / 2→3 全部被拒绝（实测：795/795 个槽位与目录标记一致，0 例外） |
| 2 | 改词条数值（限区间） | 每个槽位的 数值 输入框 | `--edit 槽:名称或id:数值` | 数值必须落在该词条自己的区间内，区间取自 `全词条数值(3稀有度…)` 的 取值集合；参考存档的 **807/807** 个已编目槽位都在区间内，0 个在区间外 |
| 3 | 按种类 / 恩宠·套装筛选 | 树上方的 筛选 行 | `list --kind <名称\|id> --grace <名称\|id>` | 筛选纯粹用于显示：它们只改变列出哪些行，绝不改变写入什么 |
| 4 | 每槽关键词匹配词条 | 在**某一个槽**里输入关键词（或 `0x646b` / `646b` / 十进制 id），只有该槽的下拉列表被缩小；回车唯一命中即选中 | `edit --search <关键词>`，或 `--edit 槽:关键词[:数值]` | **每一个**匹配都会被列出；0 个匹配和 >1 个匹配都会被连候选列表一起拒绝，所以有歧义的关键词永远不会被悄悄挑一个；空格分隔多个关键词＝必须同时命中（如 `星 恢复`）；种类 与 恩宠/套装 两个筛选互相级联，各自只列出对方结果里出现过的取值；**改写词条时会同时改写它的「种类」（游戏里词条前的图标）**，依据 `data/affix_categories.json`（15 个类别，参考存档实测 0 冲突）；**同一个物品每个「种类」只能有一个词条**（`其他` 种类不受限；同种类的 ★ 与同名固定可以各一个，不能再多）；**「同名固定」以存档 metadata 的固定属性为准**（表外词条也算，恩宠/套装槽除外）；**武士/忍者 筛选**（与种类、恩宠三向级联）；**★ 词条一定可改**（除绘卷外 ★ 不可能是固定词条），换词条时 ★ 位跟着走 |
| 5 | 无中生有 | 四个标签页上的 无中生有 区块（各自独立成框） | `create --kind … [--soul]` | 新记录从**同种类的真实样本**复制；背包满 会以 「背包已满…请先在游戏里清理背包后再添加」 被拒绝 |

实践上重要的几点说明：

* **数值区间** — 饰品词条 工作表*没有*区间列；区间住在
  `全词条数值(3稀有度…)` 的 取值集合 列里，以词条 id 的**低 16 位**为键
  （它的 代码 列是小端，例如 `BC 53` → `0x53BC`）。魂核 的区间来自
  `绘卷-魂核词条` 的 数值区间/数值集合。重新生成后的覆盖率：
**308/308** 个 饰品 和 **338/338** 个 魂核 词条带区间；其中 33 行的 数值集合
并不是整段区间，这类词条按*集合*校验（例如 0x248c 只允许 470、472、475…520，
绝不会是 471）。
  大多数 饰品词条 是**单值**的（`火抗性 +10` → 固定值 10：数值*就是*
  该词条的身份），所以数值输入框实际上只为工作簿给出真正区间的那些行
  开放——例如 `0xfb24 获得魂核时恢复体力` 158..230（本工作簿中唯一带区间的 饰品
  行）。在完全没有区间的地方，只能写入目录里的数值；
  本工具绝不猜一个。
* **固定词条优先** — 固定槽位会在数值检查*之前*被拒绝，所以它报告的是
  「同名固定词条不能修改」，而不是一个区间错误。
* **无中生有 的模板** — `find_free_slots` 用 `type == 0` 作为空槽位标记
  （在参考存档上实测：2000 个槽位中有 **465** 个，分布零散——其中 209 个
  两侧都是已占用槽位——且效果槽干净）。新记录从同 种类 中索引最小的样本
  逐字节复制，随后只重写 种类（两个
  镜像字）、等级（两个镜像字）和选定的词条。
  这是刻意的：`+0x18` 在各记录间取 6 个不同的值，而
  `+0x1c`/`+0x20`/`+0x28` 是**逐记录唯一**的（213/213），并且它们的含义并未
  解码——编造它们就等于猜，所以存档里没有样本的种类会
  以 「存档里没有 … 的样本」 被拒绝，并且不写入任何东西。固定词条来自
  模板，在这个流程里不可编辑。
* **背包已满** — 当没有 `type == 0` 的槽位剩下时，创建会拒绝并打印
  「背包已满：记录表 2000 个槽位全部被占用，请先在游戏里清理背包后再添加」。
* **只读的搜索** — `edit --search` 只加载并报告；之后存档字节
  逐字节不变（测试中有断言）。

### 参考存档

本 README 引用的每一项测量（1456 条物品记录中的 213 个饰品、
132 个已识别 魂核、807/807 个词条数值落在各自区间内、795/795 个槽位与
目录的 同名固定 标记一致、465 个空槽位、两个 八咫镜 id）都来自
同一份**参考存档**：一份普通的、未被修改的 PC 存档文件，项目是
基于它开发的，并且始终以只读方式打开。之所以这样称呼它——*参考存档*，
或*样本存档*——是因为本工具不绑定任何特定的
文件；绑定到某一个文件的只是*证据*，这也是为什么下面每一项测量
结论都会点明它。

### 它在别的玩家的存档上能用吗？

决定**什么可以被写入**的那些部分并不绑定到那个文件：

* 合法词条、数值区间、恩宠/套装、魂核 和 种类 表都是从
  `仁王3词条装备库v2.21.xlsx` 生成的，而不是从某个存档生成的；
* 识别基于证据并且失败即拒绝：饰品 需要命中目录词条，
  魂核 需要**同时**命中物品表行和 魂核 词条，任何不符合
  条件的记录都会被列为 未识别，而不是被编辑；
* 记录数组是被*定位*的，不是被假定的：扫描器在候选
  步长之间投票，胜出步长的跨度就给出了数组（见
  [布局一节](#已验证的事实与未验证的边界)）；一个没有此类
  证据的存档会被拒绝，而不是在猜出来的偏移上被编辑。

**在单个文件上测量过**的部分是字节层面的，它们在
不匹配的存档上各自都有明确的失败方式：

| 测量事实 | 如果另一份存档不一致 |
| --- | --- |
| `type == 0` 是空槽位标记（2000 个槽位中的 465 个） | 没有 `type == 0` 槽位就意味着「背包已满」，创建会被拒绝 |
| 同名固定 = 目录标记 **且** 元数据第 9 字节 `0x40` 位（795/795） | 被目录标记的槽位仍会被拒绝；但如果某份存档用别的方式编码 固定，字节证据就未经验证——在信任一个目录称为可编辑的槽位之前，先在一份副本上检查 |
| `+0x1c`/`+0x20`/`+0x28` 逐记录唯一（213/213） | create/改种类 会从**同一存档中**同种类的样本复制它们；该种类没有样本 → 以 「存档里没有 … 的样本」 被拒绝 |
| 等级 `+0x06` 镜像 `+0x08`，上限 180 | 镜像不一致或上限更高 → 该编辑被拒绝 |
| 0x5c5f = 八咫镜[武士]（来自该存档的固定词条） | id 是游戏全局的，所以这一点对每份存档都成立；它是*唯一*一个来自存档证据的物品行 |

所以：在别人的存档上，由目录驱动的功能（列出、筛选、关键词
搜索、数值区间、固定词条保护、恩宠 编辑）应当可以原样工作，而那些
需要同种类样本的写入路径，在样本缺失时会带消息被
拒绝。要检查一个新文件，请运行 `check` 和 `list`：它们会打印定位到的布局
（步长/偏移/槽位数量，以及它是否匹配参考项目捕获到的
布局），还有多少条记录被识别为饰品。

### `+0x0A` 就是物品的 +値，而且可以改

其他每个头部字都钉在了某个东西上：`+0x00`/`+0x02` 是 种类 id，
`+0x04` 是物品数量、`+0x06`/`+0x08` 是等级、`+0x0C` 是常量、`+0x30` 是
稀有度。`+0x0A` 是最后一个未知项；它现在**已在游戏内确认**：三件同种类饰品在
龙笛[武士] 物品卡上显示 +13 / +18 / +19，而这正是该字段为记录
记录 #28 / #3 / #521 保存的值。映射是 1:1 的，所以本工具像对待其他已核实字段
编辑它。在此之前测量到的关于它的东西（参考存档，213 个饰品）：

* 它取 **0 到 30 之间的 25 个不同值**，并且它是*实例*的属性，
  而不是种类的属性——74 个种类中有 42 个显示出多个值；
* 它不跟随等级（一件 Lv170 的物品可以是 0）、稀有度（神器 跨越 0..30，粗物
  始终是 0），也不跟随固定词条的数量；
* **存储的词条数值不随它改变**：在同时出现在低（≤5）和高（≥15）
  `+0x0A` 上的 82 个词条中，存储数值的平均值完全相同。所以它
  不是磁盘上的属性倍率——这也正是 等级 编辑不重写
  词条数值的原因。

改它有三种方式，都限制在 0..30（参考存档实际使用的范围；没有任何来源说明游戏
自身的上限），并且都**只**写那两个字节——不碰词条、等级或镜像：

* GUI：饰品页签逐条列出 +値，并有 `+值（0..30，字段 +0x0A）` 一行；
* CLI：`edit --record 28 --plus 13`；
* 无需子命令的脚本：

```powershell
python tools/set_plus.py --record 28 --value 13            # 演练，不写入
python tools/set_plus.py --record 28 --value 13 --write    # 真正写入（自动备份）
```

该脚本校验只有 `+0x0A` 的字节发生了变化，否则中止。最
安全的检查完全不需要写入：比较两件本来就不同的同种类物品
（例如三把 龙笛[武士]，分别为 13 / 18 / 19）。

### 绿色星号词条（★ 词条）

`绿色星号词条` 工作表列出 ★ 词条，共 257 行，而且**A 列就是它能出现的装备**
（`[饰品]`、`[魂核]`、`[近战/手臂]`…）。这 257 个 id **没有一个**出现在 饰品词条 或
绘卷-魂核词条 里（实测 0 重合），所以在接入这张表之前，本工具一个 ★ 词条都提供不了。
现在：

* **32 行适用于 饰品**（`[饰品]`、`[腿部/饰品]`、`[远程/饰品]`、`[身体/饰品/魂核]`），
  **51 行适用于 魂核**（`[魂核]`、`[近战/魂核]`、`[近战/手臂/魂核]`、
  `[身体/饰品/魂核]`）；其中 3 个 id 两者都合法，而只列出 近战/远程/防具 部位的
  行**绝不**进入饰品目录（有专门测试守着这一点）。
* **数值区间**（E/F 列）成为该词条的区间，区间外的数值在写入前就会被拒绝。
* **数值集合**（G 列起）在「不等于整段区间」时按**集合**保留：33 行以 0.1% 为单位的
  2.5 步进（例如 `0x248c` 只允许 470、472、475…520），由 `AffixEntry.values` 与
  `allows_value()` 校验，所以即使 471 落在 470..520 之内也会被拒绝。其它行的集合
  恰好就是整段区间。
* 257 行里有 3 行编码的数值被自己的区间排除（`0xdfae`：188 对 127..140，
  `0x248c`：250 对 470..520）；生成器会把目录默认值收进区间，而不是输出一个
  编辑器随后会拒绝写入的默认值。

★ 词条按名称里的 `(星)` 显示，本身就是普通可改槽位——星号位是元数据第 10 字节的
第 2 位，由 `AffixEntry.is_star` 报告。

### 修改等级

`edit --level <1..180>`（CLI）或 GUI 的 等级 行写入 `+0x06` **以及**它的镜像
`+0x08`，别的什么都不写。180 是游戏可序列化的最大值：参考
项目把有效等级推导为 `min(record +0x06, 180)`，而参考
存档正好顶到 180。该编辑拒绝 0/负数/>180，拒绝一次
空操作，也拒绝两个等级字段不一致的记录（实测在全部
213 个饰品上相等，所以不一致意味着一种本工具从未验证过的形态）。它被
标记为**谨慎修改**，因为存储的词条数值不随等级缩放：
在 135–180 级之间实测，同一种类的每一份副本都保持相同的数值（例如
除雷护身符[武士] 的 `雷属性伤害降低 +15` 在 156–170 级），所以游戏内的任何提升
都必须是游戏在载入时计算出来的——这一点存档文件无法证明。`+值`
字段是一条**独立**的编辑路径（见
[`+0x0A` 就是物品的 +値](#0x0a-就是物品的-値而且可以改)）：等级那一行从不碰它，
+值 那一行也从不碰等级。

## 安全模型

* **写入要求**：修改是写入存档**文件**的，所以游戏不能
  在内存里持有那份存档。写入前请完全关闭游戏，或者至少停在
  **标题画面**（没有载入存档，不在游戏内）；之后在游戏内保存
  会覆盖这次修改，并可能损坏该槽位。这条规则
  在每次写入前都会说明（`savefile.SAVE_WRITE_REQUIREMENT`）：在 CLI
  输出里、在 GUI 的提示行里，以及在写入确认对话框里。GUI
  还会持续显示游戏进程状态（底部绿/红线，
  在工作线程上每 3 s 复查一次），所以在点击 写入存档
  之前就能看到这个条件，而不是只在被拒绝之后才看到。
* **标题界面确认**：只要有游戏进程在运行，GUI 就会拒绝每一次写入
  （词条、+値、等级、种类、新建、恢复备份），直到操作者在窗口底部勾选
  「我确认：游戏正在运行，但停留在标题界面（尚未载入存档）」这个确认框；
  勾选在每次写入后即作废，所以下一次写入会再问一次。CLI 的等价选项是
  `--at-title-screen`（`--force-while-running` 是同一个确认的旧名）。
  不存在静默写入——游戏在运行而没有这个确认就是拒绝，而不是警告。
* 备份：`<state root>/_nioh3_equipment_affix_backup/account-<id>/slot-<NN>/` 保存一份
  解密后的 `SAVEDATA-<timestamp>-<random>-plain.bin` 以及 `backup-manifest.json`
  （schema、账号、存档位、主存档 SHA-256、明文 SHA-256）；见
  [备份与恢复](#备份与恢复)。
* 游戏进程闸门：检测到 `Nioh3.exe` / `Nioh3-Win64-Shipping.exe` 会让
  写入器失败即拒绝（`GameRunningError`，CLI 退出码 1），除非
  显式传入标题界面确认（`--at-title-screen`，或其旧名
  `--force-while-running`）。
* 静默期：存档 + `BACKUP.BIN` + 账号系统存档会被相隔 0.2 s
  哈希两次；任何变化都会以 `SAVE_SYNC_ACTIVE` 中止。
* 指纹竞态：哈希时会重新 stat 文件，如果大小/mtime 变了就中止。
* 写入路径：暂存 → 解密校验 → 复查指纹 → 原子替换 →
  再次解密校验 → 如果最终检查失败就回滚原始字节。
* 恢复路径：同一条流水线，外加对备份的清单/SHA-256 检查，
  以及为正在被替换的存档做一份新的安全备份，所以一次恢复可以
  通过恢复那份副本而撤销。当备份无法携带存档的最后 8 个字节
  （在加解密区域之外）时，它们会从当前文件保留，绝不被清零。
* GUI 会在窗口标题和页脚显示必需的免责声明，并且
  默认为 仅演练（dry run）。
